# 服务器物理引擎模拟系统技术报告

## 1. 概述

本报告定义了一套运行于服务器端的物理引擎异步模拟系统架构。系统将物理模拟完全隔离在独立线程中，通过**命令驱动**与**结果回传**机制与主线程交互，支持从资产文件加载完整物理场景，并原生支持对变化数据的**增量序列化**，以满足高性能、低带宽的服务端需求。

### 核心目标

| 目标 | 说明 |
|---|---|
| **独立物理线程** | 物理模拟在独立线程中运行，避免阻塞主逻辑 |
| **数据驱动** | 物理场景及物体完全由资产文件定义 |
| **增量同步** | 物体状态序列化时仅输出发生变化的数据，减少网络开销 |
| **并行处理** | 主线程每帧触发模拟，在恰当时机获取结果，实现并行 |

---

## 2. 系统架构

系统采用 **命令队列 + 结果队列** 的异步通信模型，物理线程与主线程间仅通过线程安全的 SPSC（Single Producer Single Consumer，单生产者单消费者）无锁队列交换数据，无其他共享可变状态，避免锁竞争。

```
┌──────────────────┐    命令队列 (SPSC)    ┌──────────────────┐
│     主线程       │ ── Spawn / Tick ──► │    物理线程      │
│  · 游戏逻辑      │                      │  · 场景管理       │
│  · 网络同步      │ ◄─ FrameResult ──── │  · 物理步进       │
│  · 序列化        │    结果队列 (SPSC)    │  · 变化提取       │
└──────────────────┘                      └──────────────────┘
```

- **主线程** 将玩家输入、系统事件等封装为命令，写入命令队列
- **物理线程** 从命令队列中读取并执行，完成物理步进后，将变换快照、碰撞事件及变化数据打包为结果，写入结果队列
- **主线程** 在完成非依赖任务后，等待本帧结果就绪，再更新游戏状态并下发网络数据

---

## 3. 物理线程设计

物理线程运行独立事件循环，通过帧号（frameId）严格匹配实现主线程与物理线程之间的时序同步，确保每帧的模拟结果与对应命令一一对应，防止队列堆积导致错帧。

### 3.1 初始化

线程启动时依次加载系统级配置文件（第 5 节）和指定的物理资产文件（如 `scene.physics`），构建完整物理世界，包括：

- 全局运行参数（重力、仿真步长、求解器迭代次数等，来自系统配置 `physics.json`）
- 静态碰撞体及其形状、材质（来自资产文件）
- 动态物体原型（质量、惯性、形状、摩擦/弹性等，来自资产文件）

加载完毕后进入主循环等待命令。

### 3.2 命令处理

物理线程持续执行以下循环：

1. 从命令队列出队一个命令（可设置超时以支持优雅退出）
2. 根据命令类型执行：

| 命令 | 说明 |
|---|---|
| `Spawn(protoId, transform)` | 基于原型动态生成刚体并加入世界 |
| `Destroy(objectId)` | 移除并销毁指定刚体 |
| `ApplyForce(objectId, force, point)` | 对指定物体施加力（世界坐标） |
| `SetVelocity(objectId, velocity)` | 直接设置物体线速度 |
| `Tick(frameId, fixedDeltaTime)` | 进入物理模拟流程（见 3.3） |

非 `Tick` 命令立即处理，`Tick` 命令为每帧模拟的触发器。

### 3.3 物理步进与结果生成

收到 `Tick` 命令后执行：

```
PhysicsWorld.Step(fixedDeltaTime);
```

模拟过程中使用**固定子步长**（如 1/120 秒）以保证仿真稳定性。确定性还原（相同输入产生相同输出）需所选物理引擎原生支持（如 Jolt Physics 的确定性模式），配合固定子步长、统一浮点路径方可实现。步进完成后：

1. **提取变换快照** — 遍历所有活跃动态刚体，记录当前 Transform（位置 + 旋转）
2. **提取碰撞事件** — 收集本帧内的碰撞事件，包括接触开始（contact-start）、接触持续（contact-persist）和接触结束（contact-end）三种类型
3. **生成变化差异（Diff）** — 对每个活跃动态物体，将其当前物理状态（位置、旋转、线速度、角速度）与上一帧保存的副本进行逐字段阈值比较（详见 6.1 节），生成变化包 `DiffPacket`（包含物体 ID、变化掩码及变化的字段值）；生成后用当前状态更新副本，作为下一帧的比较基线
4. 将上述所有数据连同 `frameId` 封装为 `PhysicsFrameResult`，推入结果队列

---

### 3.4 日志系统

物理线程拥有**独立的日志实例**，与主线程日志完全隔离，写入独立的日志文件（如 `physics_engine_2026-05-23.log`），而非共用主线程日志。日志文件名**嵌入详细日期**（精确到日），确保每次运行的日志自然分文件存储，避免覆盖，也便于按日期定位历史日志。

| 设计要点 | 说明 |
|---|---|
| **独立日志实例** | 物理线程创建并持有自己的 `Logger` 对象，不共享主线程的任何日志资源 |
| **独立日志文件** | 日志输出到独立的物理引擎专用文件，与主逻辑日志分离，便于排查和监控 |
| **无锁写入** | 物理线程日志写入无需与主线程竞争文件锁或缓冲区锁，避免日志 I/O 成为跨线程瓶颈 |
| **可配置路径** | 日志文件路径、日期格式、轮转策略、日志级别通过配置文件指定，默认文件名含 `YYYY-MM-DD` 日期 |

独立日志的设计收益：

- **故障隔离** — 物理线程崩溃前的关键日志不会因主线程日志滚动而丢失，反之亦然
- **性能隔离** — 物理线程日志 I/O 不阻塞主线程日志写入，避免高负载下日志系统成为争用热点
- **调试友好** — 排查物理模拟问题时只需关注当日的物理引擎日志文件（如 `physics_engine_2026-05-23.log`），无需从主逻辑日志中过滤物理相关条目

物理线程启动时根据 `logging.json` 配置初始化日志实例（文件名按当前日期生成，如 `physics_engine_2026-05-23.log`），线程退出时优雅关闭日志（flush 缓冲区并关闭文件句柄）。日志级别（`level` 字段）支持运行时热更新，修改配置文件后物理线程自动感知并切换，无需重启，便于现场诊断。

## 4. 资产文件设计

物理场景资产采用结构化文本或二进制格式，与渲染逻辑完全解耦。

示例结构：

```json
{
  "staticBodies": [
    {
      "id": "ground",
      "shape": { "type": "box", "halfExtents": [100, 0.5, 100] },
      "material": { "friction": 0.8, "restitution": 0.1 }
    },
    {
      "id": "door_frame",
      "shape": { "type": "box", "halfExtents": [1.2, 2.2, 0.15] },
      "material": { "friction": 0.5, "restitution": 0.05 }
    },
    {
      "id": "door_panel",
      "shape": { "type": "box", "halfExtents": [1.0, 2.0, 0.08] },
      "material": { "friction": 0.5, "restitution": 0.05 }
    }
  ],
  "dynamicPrototypes": [
    {
      "protoId": "player_default",
      "shape": { "type": "capsule", "radius": 0.5, "height": 1.8 },
      "mass": 80,
      "material": { "friction": 0.3, "restitution": 0.0 }
    }
  ]
}
```

- **`staticBodies`** — 在物理线程加载时直接构建不可移动的碰撞体
- **`dynamicPrototypes`** — 供主线程通过 `Spawn` 命令引用，物理线程根据原型克隆创建实例；原型可包含多个 `shape` 组成的复合碰撞体（compound shape）
- **`constraints`** — 定义物体间的运动约束，支持铰链（hinge）、弹簧（spring）、滑杆（slider）等类型：

> 全局物理参数（重力、步长、迭代次数等）属于系统级配置（第 5 节），不在此资产文件中定义，确保同一套物理场景可在不同运行参数下复用。

```json
"constraints": [
  {
    "type": "hinge",
    "bodyA": "door_panel",
    "bodyB": "door_frame",
    "pivot": [0, 1.5, 0],
    "axis": [0, 1, 0],
    "limits": [-1.57, 1.57]
  }
]
```

- 资产可包含自定义物理材质，完全覆盖物理世界构建需求

## 5. 物理系统级配置

系统级配置与场景资产（第 4 节）分离，存放于 `resources/physics/configs/` 目录下。配置在物理线程启动时加载，涵盖引擎运行参数、线程模型、日志策略及变化检测阈值等系统级设置。支持热更新的参数：`thresholds.json`（全部字段）、`logging.json` 中的 `level`。其余参数（如 `fixedDeltaTime`、`solverIterations`、线程模型等）需重启物理线程方可生效。

### 目录结构

```
resources/physics/configs/
├── physics.json          # 物理引擎核心运行参数
├── threading.json        # 线程模型与队列配置
├── logging.json          # 日志输出配置
└── thresholds.json       # 变化检测阈值
```

### 5.1 physics.json — 引擎核心参数

```json
{
  "gravity": [0, -9.81, 0],
  "fixedDeltaTime": 0.01667,
  "solverIterations": 10,
  "subStepCount": 2,
  "maxBodies": 4096,
  "maxContactPoints": 10240,
  "broadPhaseType": "aabb_tree"
}
```

| 字段 | 说明 |
|---|---|
| `gravity` | 重力向量（m/s²），默认 `[0, -9.81, 0]` |
| `fixedDeltaTime` | 固定仿真步长（秒），与帧率解耦 |
| `solverIterations` | 约束求解器每子步迭代次数 |
| `subStepCount` | 每帧内部子步数，子步时长 = `fixedDeltaTime / subStepCount` |
| `maxBodies` | 最大刚体数量上限，防止内存无限增长 |
| `maxContactPoints` | 最大接触点数量上限 |
| `broadPhaseType` | 宽相碰撞检测算法，可选 `aabb_tree` / `sap` |

### 5.2 threading.json — 线程模型配置

```json
{
  "threadPriority": "high",
  "affinityMask": 0,
  "commandQueueSize": 256,
  "resultQueueSize": 64
}
```

| 字段 | 说明 |
|---|---|
| `threadPriority` | 物理线程调度优先级，建议 `high` 以保证模拟按时完成 |
| `affinityMask` | CPU 亲和性掩码，`0` 表示由 OS 调度 |
| `commandQueueSize` | 命令队列容量，超出时主线程入队阻塞或降级 |
| `resultQueueSize` | 结果队列容量，用于帧堆积保护（见第 9 节） |

### 5.3 logging.json — 日志配置

```json
{
  "logDir": "./logs/physics",
  "fileName": "physics_engine",
  "dateFormat": "YYYY-MM-DD",
  "level": "info",
  "maxFileSizeMB": 50,
  "maxBackupFiles": 10
}
```

| 字段 | 说明 |
|---|---|
| `logDir` | 日志输出目录 |
| `fileName` | 日志文件基础名，与 `dateFormat` 组合生成最终文件名（如 `physics_engine_2026-05-23.log`） |
| `dateFormat` | 日期格式，默认 `YYYY-MM-DD`，嵌入文件名中 |
| `level` | 日志级别，可选 `debug` / `info` / `warn` / `error`，支持运行时热更新 |
| `maxFileSizeMB` | 单文件最大尺寸，超出后自动滚动 |
| `maxBackupFiles` | 滚动时保留的历史文件数量上限 |

日志实例及文件名生成详见第 3.4 节。

### 5.4 thresholds.json — 变化检测阈值

各维度独立可配的 epsilon 值，用于 Diff 生成时的逐字段比较（详见第 6.1 节）：

```json
{
  "positionEpsilon": 0.001,
  "rotationEpsilon": 0.00017,
  "linearVelocityEpsilon": 0.01,
  "angularVelocityEpsilon": 0.001
}
```

| 字段 | 单位 | 说明 |
|---|---|---|
| `positionEpsilon` | 米 | 位置变化低于此值视为不变 |
| `rotationEpsilon` | 弧度 | 旋转变化低于此值视为不变（约 0.01°） |
| `linearVelocityEpsilon` | m/s | 线速度变化阈值 |
| `angularVelocityEpsilon` | rad/s | 角速度变化阈值 |

## 6. 增量序列化（只序列化变化数据）

系统将增量序列化拆分为两个阶段：**物理线程生成原始变化包（Diff）**，**主线程结合客户端状态生成最终网络增量**。

### 6.1 物理线程生成 DiffPacket

每个需要同步的物体在物理线程中维护一个"上一帧物理状态"的副本，用于帧间比较。物理线程产出以下概念结构（具体实现可选用定点数压缩或 Protobuf 等序列化方案）：

```
// 概念结构，非最终 wire format
// 各字段分量数：position=3 (x,y,z), rotation=4 (quaternion), linearVel=3, angularVel=3
DiffPacket {
    uint32 objectId;       // 物体唯一标识
    uint16 changeMask;     // bit0:position, bit1:rotation, bit2:linearVel,
                           // bit3:angularVel, bit4-15: reserved
    float  values[N];      // 总长度 = Σ(popcount(bit_i) × componentCount_i)，按掩码 bit 序排列
}
```

`objectId` 的分配分两种情况：静态物体在物理线程加载资产时基于资产 ID 注册生成；动态物体在 `Spawn` 命令执行时由物理线程分配运行时 ID。ID 到物体的映射关系由注册表统一维护，确保主线程可通过 ID 唯一引用每个物体。

比较基于**物理层变化阈值（physics epsilon）**（如位置变化 < 1mm、旋转角度 < 0.01° 则视为不变），仅当有字段变化超过此 epsilon 时才生成 `DiffPacket`。此阈值各维度独立可配置，见第 5.4 节。物理线程产出的即为最原始的、仅包含变化的物理数据，不涉及任何客户端确认状态。

### 6.2 主线程生成网络增量

主线程维护每个客户端-物体的**复制状态跟踪器**，记录该客户端上次确认的物体状态（位置、旋转等）。收到 `PhysicsFrameResult` 后：

1. 对每个物体，使用物理 Diff 更新自己维护的"权威状态"
2. 结合该客户端上次确认状态与权威状态，计算需要下发的增量变化（仅包含变化超过网络同步阈值的字段，此阈值独立于物理层 epsilon，可按客户端带宽策略单独配置）
3. 将增量序列化后发送到客户端
4. 收到客户端 ACK 后，将"已确认状态"更新为本次下发的权威状态；若丢包重传超限，则下次同步时自动退化为全量同步

> 此设计使得网络同步策略（全量/增量、可靠性等）完全由主线程控制，物理线程不感知网络细节，满足"只序列化变化数据"的要求。

## 7. 主线程帧循环与结果获取时机

主线程每帧执行严格的时序流程，最大化利用物理线程的并行计算能力。`fixedDeltaTime` 为固定仿真步长，与系统配置中的 `subStepCount` 协同决定每子步时长（子步时长 = `fixedDeltaTime / subStepCount`），与渲染帧率解耦：

```
主帧循环：

1. 生成新帧号 frameId，处理网络输入，生成物理命令并写入命令队列
2. 写入 Tick(frameId, fixedDeltaTime) 命令，触发物理线程开始模拟
3. 执行非物理依赖任务（AI 决策、定时器、聊天处理等）
4. 调用 FetchResult(frameId, timeout) 等待本帧物理结果
   （一般此时物理线程早已完成，等待时间极短）
5. 使用结果中的变换快照更新游戏对象状态
6. 处理碰撞事件，触发伤害、拾取等游戏逻辑
7. 基于结果中的 Diff 数据，为各客户端构建增量同步包并发送
8. 进入下一帧循环
```

### 获取结果时机的合理性

- 步骤 2 触发模拟后，物理线程立即开始计算，主线程不空闲等待，转而处理步骤 3 中的并行任务
- 当主线程必须依赖物理结果继续（步骤 5-7）时，物理模拟基本已经完成，实现**几乎零等待**的高效并行

### 超时与容错

`FetchResult` 使用带超时的等待，若物理线程崩溃或严重延迟，主线程可安全进入异常处理流程（详见第 9 节容错与健壮性），避免整个服务瘫痪。

## 8. 线程安全与通信机制

| 机制 | 说明 |
|---|---|
| **命令队列** | 单生产者单消费者（SPSC）无锁队列（如 `moodycamel::ReaderWriterQueue`），物理线程为消费者，主线程为生产者 |
| **结果队列** | 同样采用无锁 SPSC 队列，物理线程将结果 `PhysicsFrameResult` 通过移动语义整体移动入队，杜绝跨线程拷贝；内部数据使用预分配容量的 `std::vector` 存储，可结合对象池复用底层内存，杜绝每帧动态分配 |
| **帧号同步** | `PhysicsFrameResult` 严格绑定帧号，主线程仅接受期望帧号的结果，防止因队列堆积导致错帧 |

---

## 9. 容错与健壮性

- **物理线程异常退出** — 通过原子标志位或特殊哨兵命令通知物理线程退出；主线程检测到结果超时后标记线程需重启，并在安全点（无进行中命令的空闲状态）重新初始化物理世界
- **物理系统配置加载失败** — 物理线程启动时依次加载系统配置（第 5 节）与场景资产（第 4 节），任一加载失败均将错误汇报给主线程，阻止服务进入可服务状态
- **帧堆积保护** — 若物理线程耗时超过主线程帧间隔，结果队列可能堆积；系统可设置最大待处理帧数，超过后降级处理（跳过非关键物理结果，或在可接受精度损失的前提下临时降低子步数，或通知运维）；降低子步数会改变模拟精度与确定性，仅应作为临时缓解措施
- **变化阈值可配置** — Diff 生成使用的 epsilon 值（位置、旋转、线速度、角速度等各维度独立配置）由 `resources/physics/configs/thresholds.json` 定义（见第 5.4 节），可依据场景需求和带宽预算灵活调整

---

## 10. 总结

本设计通过**独立物理线程、资产驱动场景、帧号同步与增量序列化分离**，构建了一个高性能、可扩展的服务端物理模拟系统。

### 关键优化点

| 优化点 | 说明 |
|---|---|
| **完全并行** | 主线程在物理模拟期间执行无依赖任务，有效隐藏延迟 |
| **低带宽序列化** | 变化数据由物理线程直接提取，主线程按客户端状态二次增量，大幅减少同步数据量 |
| **高可靠性** | 帧号严格匹配、超时保护与无锁通信，确保系统在异常情况下仍可控制 |
