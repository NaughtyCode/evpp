================================================================================
引擎 Profiler 系统 — Perfetto 集成实施计划
基于 ./src/thirdparty/perfetto/perfetto.h (amalgamated 单头文件, 7.9MB)
================================================================================

零、perfetto amalgamated 关键信息
--------------------------------------------------------------------------------
. 构建类型: kInProcessBackend (无需外部 traced 守护进程)
. 引入方式: #include "thirdparty/perfetto/perfetto.h" (纯头文件，无需链接额外库)
. 核心初始化: perfetto::Tracing::Initialize(args) + perfetto::TrackEvent::Register()
. Session 创建: perfetto::Tracing::NewTrace(kInProcessBackend)
. Session API: Setup(config) → Start() / StartBlocking()
               → Flush(callback) / FlushBlocking()
               → Stop() / StopBlocking()
               → ReadTrace(callback) / ReadTraceBlocking()
. 上游宏:   TRACE_EVENT (RAII scope), TRACE_EVENT_BEGIN, TRACE_EVENT_END,
            TRACE_EVENT_INSTANT (零时长瞬时事件), TRACE_COUNTER
. Category:  PERFETTO_DEFINE_CATEGORIES(perfetto::Category("name")) 在头文件声明
. 静态存储: PERFETTO_TRACK_EVENT_STATIC_STORAGE() 必须出现在唯一一个 .cc 文件中
. 线程安全: perfetto 内部线程安全，可在多线程同时使用
. 编译影响: perfetto.h 为 7.9MB amalgamated 头文件, 不可在公共头文件中包含。
  仅在 profiler_core.cc 和 profiler_categories.h 中直接包含 perfetto.h;
  profiler_macros.h 在 ON 模式包含 profiler_categories.h (间接引入);
  业务 .cc 只 include profiler_macros.h (轻量)。建议将 perfetto.h 加入 PCH。

一、前提与约束
--------------------------------------------------------------------------------
. perfetto SDK 位置: ./src/thirdparty/perfetto/perfetto.h (amalgamated, 含全部实现)
. profiler 新代码全部放入 ./engine/profiler/ 目录
. profiler 全部代码用 C++ 宏包裹，通过 CMake option 控制 (默认 OFF，开发/测试时 ON)
. 宏在 OFF 状态下展开为空操作，确保零运行时开销和零编译产物增长
. 引擎各功能模块增加 trace event 桩点
. 提供丰富的 C++ 宏封装，对标 perfetto 原生宏并降低使用门槛
. 提供完整的 profiler 启动、停止机制及配套 API (Stop→Start 即可实现重启)
. 引擎主要函数和流程节点均打上 profiler 桩
. 物理系统与主线程共享 TracingSession (推荐) 或使用独立 Session (备选, 需实测验证)

二、编译开关设计
--------------------------------------------------------------------------------
. CMake option: ENGINE_PROFILER_ENABLED (BOOL, 默认 OFF)
  对标 ENGINE_PHYSICS_ENABLED 的模式，统一 ENGINE_ 前缀

. ENGINE_PROFILER_ENABLED=OFF:
    - 所有 profiler 宏展开为空操作 (do {} while(0) 或 /* nothing */)
    - 不包含 perfetto.h，不触发任何 perfetto 符号
    - 零编译开销，零二进制体积增长

. ENGINE_PROFILER_ENABLED=ON:
    - add_definitions(-DENGINE_PROFILER_ENABLED)
    - profiler 宏展开为实际 perfetto tracing 调用
    - 包含路径: ${PROJECT_SOURCE_DIR} 已在 CMake 中 (engine/CMakeLists.txt:14)，
      可直接 #include "thirdparty/perfetto/perfetto.h"，无需额外配置
    - 可通过运行时 API 控制 session 启停

三、文件结构
--------------------------------------------------------------------------------
engine/profiler/
├── profiler_macros.h        # 用户侧宏 (可独立 include, 不依赖 profiler_core.h)
├── profiler_categories.h    # PERFETTO_DEFINE_CATEGORIES(...) 声明 (也需 ON/OFF 宏守卫)
├── profiler_core.h          # ProfilerManager 单例 + ProfilerConfig 结构体 (ENGINE_API)
├── profiler_core.cc         # 实现 + PERFETTO_TRACK_EVENT_STATIC_STORAGE() (唯一位置)
└── profiler_events.h        # 引擎级便捷宏 (帧、物理、脚本等, 组合基础宏, include profiler_macros.h)
                              #   在 ENGINE_PROFILER_ENABLED 宏守卫内声明帧循环复用的
                              #   inline perfetto::CounterTrack (需要 #ifdef 包裹, OFF 时不可引用 perfetto 类型):
                              #     g_frame_no_track, g_frame_dt_track, g_frame_time_track

扩展名使用 .cc 与引擎现有代码保持一致 (见 engine/CMakeLists.txt)。
所有新头文件使用 #pragma once，与引擎现有代码保持一致 (见 engine/engine/engine.h:1)。
PERFETTO_TRACK_EVENT_STATIC_STORAGE() 必须放在唯一一个 .cc 中，选择 profiler_core.cc。
该宏必须与 PERFETTO_DEFINE_CATEGORIES 在同一命名空间作用域 — 若 categories 声明在全局
作用域 (不在 namespace engine 内)，则 STATIC_STORAGE 也必须在全局作用域调用 (放在
profiler_core.cc 文件顶部，namespace engine { 之前)。

Include 策略:
. profiler_macros.h — 轻量头文件，业务代码按需 include (仅在需要打桩的 .cc 中引入)
. profiler_categories.h — 由 macros.h 自动包含 (用户无需手动 include)
. profiler_core.h — 仅在 Engine::Init() 等需要控制 session 的地方 include
. profiler_events.h — 按需 include (仅使用引擎专用宏时)

四、C++ 宏设计
--------------------------------------------------------------------------------

4.1 基础宏 — 封装 perfetto 原生宏，统一 ENGINE_PROFILE_ 前缀:

    cat 参数说明: 所有 cat 参数均为字符串字面量 (如 "engine")，对应 PERFETTO_DEFINE_CATEGORIES
                 中声明的 Category 名称。perfetto 在运行时按字符串匹配查找 category。

    (a) Category 声明 (直接放在 profiler_categories.h 中，无需包装宏):
        直接使用 PERFETTO_DEFINE_CATEGORIES(perfetto::Category("name").SetDescription("desc"), ...)

    (b) RAII 区间事件 (推荐优先使用):
        ENGINE_PROFILE_SCOPE(cat, name, ...)
          → TRACE_EVENT(cat, name __VA_OPT__(,) __VA_ARGS__)
          变参用于传入 debug annotation (如 "frame_no", frame_count_) 或 Flow Event 标注
          注意: perfetto 原生的 TRACE_EVENT 本身就是 RAII scoped，不是瞬时事件

    (c) 手动区间事件 (begin/end 配对，用于跨作用域场景):
        ENGINE_PROFILE_BEGIN(cat, name, ...)
          → TRACE_EVENT_BEGIN(cat, name __VA_OPT__(,) __VA_ARGS__)
        ENGINE_PROFILE_END(cat)
          → TRACE_EVENT_END(cat)

    (d) 瞬时事件 (零时长标记点):
        ENGINE_PROFILE_INSTANT(cat, name)
          → TRACE_EVENT_INSTANT(cat, name)

    (e) 计数器 (数值 track，用于帧率、内存用量等):
        ENGINE_PROFILE_COUNTER(cat, name, value)
          → TRACE_COUNTER(cat, perfetto::CounterTrack(name), value)
        注意: 每次调用 ENGINE_PROFILE_COUNTER 会构造新的 CounterTrack (新 UUID),
        导致同一名称的计数器在 UI 中显示为多条独立 track 而非单一时间序列。
        对于高频计数器 (帧号、帧耗时等), 推荐在 .cc 中创建 static track 复用:
          static perfetto::CounterTrack s_frame_track("frame_number");
          ENGINE_PROFILE_COUNTER_TRACK(cat, track, value)
            → TRACE_COUNTER(cat, track, value)  // 复用预创建 track, 形成连续时间序列

    (f) 便捷函数追踪:
        ENGINE_PROFILE_FUNC()
          → ENGINE_PROFILE_SCOPE("engine", __func__)
          (__func__ 是 C++11 标准标识符, 跨平台兼容, 展开为裸函数名, 如 "FrameLoop";
           如需类名限定可用 __FUNCTION__ (MSVC) 或 __PRETTY_FUNCTION__ (GCC/Clang),
           但会降低跨平台一致性, 推荐坚持 __func__)

4.2 引擎专用宏 — 组合基础宏，对应引擎实际生命周期:

    (a) 帧循环 (对应 engine/engine/engine.cc Tick + FrameLoop 实际代码流程):
        ENGINE_PROFILE_TICK()                       — Engine::Tick() 入口 [SCOPE]
                                                      (包裹 FrameLoop + last_work_time_ 更新;
                                                       不含帧率控制等待, 等待在宏之前检查)
        ENGINE_PROFILE_FRAME_BEGIN(frame_no, dt_ms)  — 帧开始 [BEGIN], 记录帧号和帧间隔
                                                       (多语句宏: 先 COUNTER_TRACK 再 BEGIN, 用 do{}while(0) 包裹)
                                                       使用 profiler_events.h 中预声明的 inline CounterTrack
                                                       (g_frame_no_track, g_frame_dt_track) 确保帧号/帧间隔
                                                       形成连续时间序列, 而非每帧一个独立 track
        ENGINE_PROFILE_FRAME_END(elapsed_ms)         — 帧结束 [END], 记录帧耗时
                                                       (多语句宏: 先 COUNTER_TRACK 再 END, 用 do{}while(0) 包裹)
                                                       使用 g_frame_time_track 记录帧耗时, 再 END 关闭帧切片
        ENGINE_PROFILE_SLOW_FRAME(elapsed_ms, threshold_ms) — 慢帧标记 [INSTANT],
                                                       elapsed > threshold 时触发，用于定位性能尖峰
        ENGINE_PROFILE_TIMER_UPDATE()                — TimerManager::update() [SCOPE]
        ENGINE_PROFILE_PHYSICS_TICK(frame_no)        — PhysicsEngineBridge::Tick() [SCOPE]
        ENGINE_PROFILE_SCRIPT_UPDATE()               — ScriptVM::UpdateScript() [SCOPE]
        ENGINE_PROFILE_PHYSICS_FETCH(frame_no)       — PhysicsEngineBridge::FetchResult() [SCOPE]
        ENGINE_PROFILE_SCRIPT_CALLBACK()             — PhysicsEngineBridge::UpdateScript() [SCOPE]
        注: [BEGIN]/[END] 为手动配对, [SCOPE] 为 RAII 自动结束 (需用 { } 控制作用域)

    (b) 物理线程 (对应 engine/physics/physics_thread.cc EventLoop):

        注: CollectTransforms, CollectCollisionEvents, GenerateDiffs 实际上在
        PhysicsWorld::Step() 内部被调用 (physics_world.cc:439-441)，而非 EventLoop
        的直接阶段。各宏应在 Step() 内部打桩，trace 层级为:
          PhysicsStep (system_.Update + 后处理, 对应 PhysicsWorld::Step(float delta_time, uint64_t frame_id))
          ├── Transform  (CollectTransforms)      — physics_world.cc:439
          ├── Collision  (CollectCollisionEvents)  — physics_world.cc:440
          └── Diff       (GenerateDiffs)           — physics_world.cc:441

        ENGINE_PROFILE_PHYSICS_CMD_DEQUEUE()   — 命令出队 [SCOPE]
                                                (若 cmd.type == Tick 则用 std::get_if<TickArgs>(&cmd.args)
                                                 提取 frame_id 存入 thread_local; 非 Tick 命令将 frame_id 置为
                                                 UINT64_MAX 作为无效标记, 后续宏仅在 frame_id != UINT64_MAX
                                                 时才写 flow annotation)
        ENGINE_PROFILE_PHYSICS_STEP(delta_time)   — PhysicsWorld::Step() [SCOPE]
                                                (delta_time 作为 debug annotation 记录: "delta_time", delta_time;
                                                 通过 thread_local 读取 frame_id 用于 TerminatingFlow)
        ENGINE_PROFILE_PHYSICS_COLLISION()     — 碰撞检测 [SCOPE] (Step 内部嵌套)
        ENGINE_PROFILE_PHYSICS_TRANSFORM()     — 变换收集 [SCOPE] (Step 内部嵌套)
        ENGINE_PROFILE_PHYSICS_DIFF()          — 状态差异生成 [SCOPE] (Step 内部嵌套)
        ENGINE_PROFILE_PHYSICS_RESULT_ENQUEUE() — 结果入队 [SCOPE]

    (c) 脚本系统:
        ENGINE_PROFILE_SCRIPT_DOFILE(path)   — 加载脚本文件 [SCOPE]
        ENGINE_PROFILE_SCRIPT_EXPORT(name)   — script bind 注册 [SCOPE] (如 "log", "timer")

    (d) 跨线程流事件 (Flow Event, 标记因果关系):
        ENGINE_PROFILE_FLOW_BEGIN(cat, name, flow_id)
          → TRACE_EVENT_BEGIN(cat, name, perfetto::Flow::ProcessScoped(flow_id))
            (在发射端创建切片并标记流起点, flow_id 通常用 frame_count_)
        ENGINE_PROFILE_FLOW_END(cat)
          → TRACE_EVENT_END(cat)
            (关闭最近一个该 category 的 BEGIN 切片; flow 标注已在 BEGIN 端,
             END 端无需额外参数 — TRACE_EVENT_END 虽支持 Track 参数用于
             异步事件配对, 但 ENGINE_PROFILE 的 flow 体系通过同 category
             的后进先出栈自然匹配, 无需 Track 去歧义)
        ENGINE_PROFILE_FLOW_TERMINATE(cat, name, flow_id)
          → TRACE_EVENT_BEGIN(cat, name, perfetto::TerminatingFlow::ProcessScoped(flow_id))
            (在接收端创建切片并标记流终点; 需与 ENGINE_PROFILE_FLOW_END(cat) 配对关闭)

        跨线程使用模式:
          发射线程:  FLOW_BEGIN(cat, name, id);  ...work...  FLOW_END(cat);
          接收线程:  FLOW_TERMINATE(cat, name, id);  ...work...  FLOW_END(cat);
        Flow 标注分别在两端的 BEGIN 上, END 仅为普通关闭; 通过相同 flow_id 关联。

        注意: Flow Event 是 TRACE_EVENT_BEGIN 切片上的附加标注 (annotation),
        不是独立事件。实际使用时推荐将 flow 标注直接整合进引擎宏内部
        (主线程 PHYSICS_TICK 内部用 Flow::ProcessScoped,
         物理线程 PHYSICS_STEP 内部用 TerminatingFlow::ProcessScoped),
        减少显式调用。此处提供独立宏作为备选手动方案。
        用于连接主线程 Tick → 物理线程 Step → FetchResult 返回的因果关系链。

    引擎专用宏的展开语义:
    . 4.2(a) 帧循环宏 — TICK, FRAME_BEGIN, PHYSICS_xxx, SCRIPT_xxx 等均为 SCOPE
      宏 (内部使用 ENGINE_PROFILE_SCOPE)，在最近的封闭 } 处自动结束。
      FRAME_BEGIN/FRAME_END 例外，使用手动 BEGIN/END 配对以包裹整帧。
      各阶段宏嵌套形成层级结构:
        Tick                        ← ENGINE_PROFILE_TICK() 最外层
        └── Frame                   ← FRAME_BEGIN + FRAME_END 配对
            ├── TimerUpdate
            ├── PhysicsTick
            ├── ScriptUpdate
            ├── PhysicsFetch
            └── ScriptCallback
    . 4.2(b) 物理线程宏 — 均为 SCOPE 宏，SEMANTICS 同 4.2(a)。
    . 带参数的 SCOPE 宏 (如 PHYSICS_TICK(frame_no), PHYSICS_STEP(delta_time)):
      额外参数作为 perfetto debug annotation 记录到切片上
      (e.g. "frame_no", frame_no 或 "delta_time", delta_time)，可在 trace 中按值筛选。
    . 使用方式: 每个引擎宏后紧跟被检测的代码，用 { } 创建显式作用域以控制切片边界。
      详见 4.3 示例。

4.3 使用示例 (FrameLoop 打桩后):

    // trace 层级: Tick → Frame → [TimerUpdate, PhysicsTick, ScriptUpdate,
    //                                 PhysicsFetch, ScriptCallback]
    // TICK 和各阶段宏均为 SCOPE (RAII), FRAME_BEGIN/END 为手动配对

    void Engine::Tick() {
        if (!running_) return;
        auto now = std::chrono::steady_clock::now();
        if (now - last_work_time_ < frame_interval_) return;

        { ENGINE_PROFILE_TICK();
        FrameLoop();
        last_work_time_ = std::chrono::steady_clock::now();
        }  // Tick slice ends
    }

    void Engine::FrameLoop() {
        auto frame_start = std::chrono::steady_clock::now();

        ENGINE_PROFILE_FRAME_BEGIN(frame_count_,
            std::chrono::duration_cast<std::chrono::milliseconds>(
                frame_start - last_frame_time_).count());

        { ENGINE_PROFILE_TIMER_UPDATE();
        TimerManager::instance().update();
        }  // TimerUpdate slice ends

        { ENGINE_PROFILE_PHYSICS_TICK(frame_count_);
        PhysicsEngineBridge::Instance().Tick(frame_count_, fixed_delta_time_);
        }  // PhysicsTick slice ends

        { ENGINE_PROFILE_SCRIPT_UPDATE();
        if (script_vm_) script_vm_->UpdateScript();
        }  // ScriptUpdate slice ends

        { ENGINE_PROFILE_PHYSICS_FETCH(frame_count_);
        auto result = PhysicsEngineBridge::Instance().FetchResult(frame_count_, 5);
        if (result) {
            { ENGINE_PROFILE_SCRIPT_CALLBACK();
            PhysicsEngineBridge::Instance().UpdateScript();
            }  // ScriptCallback slice ends
        }
        }  // PhysicsFetch slice ends

        auto elapsed = std::chrono::duration_cast<std::chrono::milliseconds>(
            std::chrono::steady_clock::now() - frame_start).count();
        ENGINE_PROFILE_FRAME_END(elapsed);  // Frame slice ends
    }

五、核心 API 设计
--------------------------------------------------------------------------------

5.1 ProfilerConfig 结构体:

    struct ENGINE_API ProfilerConfig {
        std::string  output_path     = "trace.perfetto-trace";  // 相对路径, 基于 CWD;
                                                               // 生产环境须设为绝对路径,
                                                               // 多次 session 建议追加时间戳避免覆盖
        uint32_t    buffer_size_kb   = 32768;   // 每个 buffer 32MB
        uint32_t    duration_ms      = 0;       // 0 = 手动停止; 非 0 时到达时限自动停止
        uint32_t    flush_interval_ms = 5000;
        bool        write_into_file  = false;   // true = 直接写文件, 避免内存积累
                                                // false 时数据存于 ring buffer, 留意 buffer_size_kb 上限
    };

    实现建议: SaveTrace() 内部在 output_path 追加时间戳后缀 (如
    "trace_20260524_143021.perfetto-trace"), 避免多次 session 的 trace 文件互相覆盖。
    同时提供 SaveTraceExact() 严格使用 config 中的原始路径, 供已知确切路径时使用。

    ProfilerConfig → perfetto::TraceConfig 转换逻辑:
    . 创建 BufferConfig: set_size_kb(buffer_size_kb), set_fill_policy(RING_BUFFER)
    . 创建 DataSource: ds_cfg.mutable_config()->set_name("track_event")
      可选 category 过滤: 构造 TrackEventConfig → add_enabled_categories() /
      add_disabled_categories() → SerializeAsString() →
      ds_cfg.mutable_config()->set_track_event_config_raw(raw);
      默认不设置 (全部启用)
    . 创建 TraceConfig: add_buffers(), add_data_sources(), set_duration_ms(),
      set_write_into_file(), set_output_path(), set_flush_period_ms()
    . 使用 perfetto::protos::gen::TraceConfig (生成的 C++ protobuf 类)
    . 注意: set_write_into_file() / set_output_path() 在 kInProcessBackend 下可能
      不被支持 (这些字段原为系统级 traced 服务设计)。可靠的文件写入路径是:
      StopBlocking() → ReadTraceBlocking() → ProfilerManager::SaveTrace() 手动写盘。
      write_into_file 默认为 false, 用户显式启用时需在目标 perfetto 版本上实测验证。

    初始化流程:
    1. 构造 TracingInitArgs:
       perfetto::TracingInitArgs{
           .backends = perfetto::kInProcessBackend,
           .shmem_size_hint_kb = cfg.buffer_size_kb,  // shmem 不小于 buffer
       }
    2. perfetto::Tracing::Initialize(args)
    3. perfetto::TrackEvent::Register()
    4. 若任一步失败, Initialize() 返回 false, initialized_ 保持 false
    5. 后续所有 ProfilerManager 操作检查 initialized_, 未初始化时是空操作
    6. 错误处理: Initialize() 内部通过 ENGINE_LOG_ERROR 记录失败原因;
       StartSession() 的 NewTrace + Setup + StartBlocking 任一步失败时返回 false
       (已创建的 partial session 立即释放), 并通过日志记录具体失败步骤。
       业务层调用 StartSession() 应检查返回值, 失败时 tracing 静默不可用,
       不影响引擎正常逻辑 (fail-open 策略)。

5.2 ProfilerManager 单例:

    // profiler_core.h 需要的前向声明和头文件:
    #include <cstdint>          // uint32_t
    #include <memory>           // std::unique_ptr
    #include "engine_export.h"  // ENGINE_API
    namespace perfetto { class TracingSession; }  // 前向声明, 避免在 .h 中包含 perfetto.h;
                                                   // 注意: std::unique_ptr<perfetto::TracingSession>
                                                   // 持有不完整类型是合法的, 但必须将 ~ProfilerManager()
                                                   // 定义在 profiler_core.cc 中 (而非 = default 在头文件),
                                                   // 否则编译器会在头文件隐式生成 deleter 时要求完整类型

    class ENGINE_API ProfilerManager {
    public:
        static ProfilerManager& Get();

        // 生命周期 — Engine::Init() 中调用 Initialize, Cleanup() 中调用 Shutdown
        bool   Initialize(const ProfilerConfig& cfg);  // true=初始化就绪 (首次或已初始化幂等);
                                                       // false=perfetto 底层调用失败, 此时
                                                       // initialized_ 保持 false, 需检查日志
        void   Shutdown();       // 安全关闭 (自动停止活跃 session, flush, 释放资源)

        // Session 控制
        bool   StartSession();   // 返回 false 表示创建失败; 若已有活跃 session 则先停止旧的
        void   StopSession();    // 无活跃 session 时是空操作 (幂等)

        // 状态查询
        bool   IsActive() const;               // 是否有活跃 session
        static bool IsEnabled();               // 编译期开关

        // 数据操作
        void              Flush();             // 活跃 session 时有效, 否则空操作
        std::vector<char> ReadTrace();         // Stop 后读取, 无数据时返回空 vector
        void              SaveTrace();                     // 使用 config_.output_path + 时间戳后缀保存
        void              SaveTraceExact(const std::string& path);  // 严格按给定路径保存, 不做修改

    private:
        ProfilerConfig config_;
        std::unique_ptr<perfetto::TracingSession> session_;
        bool initialized_ = false;
    };

    生命周期规则:
    . Initialize() 幂等 — 首次调用执行 perfetto 全局初始化; 重复调用返回 true
      (无操作), 不改变状态。如需更换配置, 须先 Shutdown() 再 Initialize(new_cfg)。
    . 不可在 Initialize() 和 Shutdown() 调用期间引入数据竞争 — ProfilerManager 的
      状态变更 (initialized_, session_) 依赖调用者保证串行化, 不在内部加锁。
      StartSession/StopSession/Flush 同样假定由同一线程或外部同步机制调用。
    . StartSession() 幂等 — 若已有活跃 session 则隐式 StopSession() 再创建新的
    . StopSession() 幂等 — 无活跃 session 时是空操作
    . Shutdown() 幂等 — 可安全多次调用, 自动清理所有资源
    . ReadTrace() 仅在 StopSession() 后有效 — 活跃 session 时返回空 vector
    . Shutdown() 调用时机 — 必须在 Engine::Cleanup() 末尾, 所有子系统停止之后调用,
      确保各线程的 trace 数据已全部写入。顺序: 先停止子系统, 再 Shutdown profiler。

5.3 物理线程 Trace 方案:

    方案选择: 优先尝试 "单一 session + 多线程写入" 方案 (简洁), 备选独立 session。

    方案 A (推荐): 单一 Session, 双线程写入
    . 主线程创建 TracingSession (通过 ProfilerManager::StartSession)
    . 物理线程直接使用 perfetto 宏写入同一 session — perfetto 内部线程安全,
      多线程可同时写入, UI 中按线程 track 天然隔离
    . 无需在物理线程中管理 session 生命周期, 代码最简单
    . 实现: 将 ENGINE_PROFILER_ENABLED 编译定义传递给 physics 模块即可,
      physics .cc 文件 include profiler_macros.h 后所有宏直接生效
    . 跨线程因果关系: 通过 Flow Event 连接 —
      PHYSICS_TICK 内部用 Flow::ProcessScoped, PHYSICS_STEP 内部用
      TerminatingFlow::ProcessScoped, 二者共享 frame_id 作为 flow_id

    方案 B (备选): 独立 TracingSession
    . PhysicsThread 内部自行创建和管理 TracingSession (直接调用
      perfetto::Tracing::NewTrace(kInProcessBackend))
    . 前提: 验证 kInProcessBackend 支持多个并发 TracingSession
      (perfetto 文档表明支持, 但需在目标版本上实测确认)
    . 依赖: 必须先调用 ProfilerManager::Initialize() (全局 perfetto 初始化),
      再启动物理线程 — 物理线程 session 可用但全局 init 由 ProfilerManager 保证
    . 物理线程停止时: 在 EventLoop 退出前调用 StopBlocking() + ReadTraceBlocking()，
      将 trace 数据通过文件传回主线程合并保存
    . 优点: 可对物理线程单独启停 tracing (如只分析物理性能时无需主线程 trace 数据)

七、引擎打桩点清单 (严格对齐 FrameLoop 实际代码)
--------------------------------------------------------------------------------

7.1 帧循环 (engine/engine/engine.cc Tick + FrameLoop, 第181-290行):

    - PhysicsEngineBridge::UpdateScript() — Lua 碰撞回调

7.2 物理线程 (engine/physics/physics_thread.cc EventLoop):

7.4 定时器 (engine/core/timer/):
    - TimerManager::update() 内部遍历
    - 到期定时器回调触发
    - 定时器调度 (schedule) / 取消 (cancel)

7.5 引擎生命周期 (engine/engine/engine.cc):
    - Engine::Init() — ProfilerManager::Initialize() (最早), 日志初始化,
      TimerManager 创建, ScriptVM 创建
      注: Initialize() 之后应尽早调用 StartSession() — 若在 Init() 末尾调用,
      则 Init 内部的桩点不会进入 trace。推荐在 Init() 中 Initialize() →
