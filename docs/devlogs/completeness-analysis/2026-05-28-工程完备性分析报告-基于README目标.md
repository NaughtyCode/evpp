## 三、未完成功能与不足

### 3.1 阻塞性未完成项 (影响功能可用性)

#### 3.1.1 AOI 子系统未编译入构建 (P2-1)

**现状**: 源代码存在 (`src/runtime/aoi/spatial_index.h/cc`, `aoi_manager.h/cc`) 且单元测试存在 (`test_aoi.cpp`)，但在 `script_bind.cc:51-56` 中被 `#if 0` 守卫:

```cpp
#if 0  // AOI subsystem not yet compiled (aoi .cc files not in build)
```

**影响**: AOI (Area of Interest) 是游戏服务器的核心子系统——管理玩家视野、空间广播、九宫格同步。没有它，Space 层只能做全量广播，无法支撑 MMO 规模的场景。

**根因**: CMakeLists.txt 中未添加 AOI 源文件。

#### 3.1.2 ORM + Cache 子系统未编译入构建 (P2-2)

**现状**: 源代码存在 (`src/runtime/database/orm.h`, `cache.h`) 且单元测试存在 (`test_orm.cpp`, `test_cache.cpp`)，但在 `script_bind.cc:57-62` 中被 `#if 0` 守卫:

```cpp
#if 0  // ORM subsystem not yet compiled (orm_bind.cc requires EntityCache fixes)
```

**影响**: Lua 侧无法使用 ORM 风格的数据访问（`orm:find()`, `orm:insert()`），仍需手写 BSON 构造。EntityCache 无法使用——每次数据访问都走完整的 SPSC → DBThread → MongoDB 网络 IO。

**根因**: 注释说 "EntityCache fixes"，暗示 cache.h 存在需要修复的问题。

#### 3.1.3 RPC 框架无 Lua 绑定 (P2-3)

**现状**: C++ 源代码存在 (`src/runtime/rpc/rpc_client.h/cc`, `rpc_server.h/cc`, `rpc_protocol.h`) 且单元测试存在 (`test_rpc.cpp`)，但:
- 无 `src/runtime/script/rpc_bind.cc`（Lua 绑定层）
- 未在 `script_bind.cc` 中 `ExportRpc()`
- engine.cc 中无 RPC 初始化或 Tick 调用

**影响**: 服务器间通信需要手写协议解析——这对微服务/分布式架构是基本需求。

#### 3.1.4 Auth 框架无 Lua 绑定 (P2-4)

**现状**: C++ 源代码存在 (`src/runtime/auth/auth_backend.h/cc`, `session_manager.h/cc`) 且单元测试存在 (`test_auth.cpp`)，但:
- 无 `src/runtime/script/auth_bind.cc`
- 未在 `script_bind.cc` 中 `ExportAuth()`
- engine.cc 中未集成 Connection 认证流程

**影响**: 玩家登录认证需要在 Lua 侧手写，无法使用框架提供的 session 管理和 token 验证。

#### 3.1.5 Cache 子系统无 Lua 绑定 (P2-2 的一部分)

**现状**: `src/runtime/database/cache.h` 存在且 `test_cache.cpp` 存在，但:
- 无 `src/runtime/script/cache_bind.cc`
- `script_bind.cc` 中无 `ExportCache()`
- Cache 仅在 C++ 侧可用

### 3.2 设计质量不足 (影响开发效率和可维护性)

#### 3.2.1 网络绑定样板代码未消除 (P1-1, ~1500 行重复)

**现状**: 6 个协议绑定文件仍使用手动 lightuserdata + disposed 模式。以 `net_tcp_server_bind.cc` 为例，仍有 38 处 `disposed`/`lightuserdata`/`luaL_ref`/`luaL_unref` 引用。MongoDB 绑定层的 `bind_util.h` (GetUserdata<T>/NewUserdata<T> 模板) 的成功模式未被推广到网络层。

**影响**: 
- 新增协议绑定需复制 ~300 行样板代码
- 修改生命周期管理模式需跨 6 个文件同步
- 新增开发者的学习曲线陡峭

**根因**: 工作量评估约 800 LOC + 需要重构所有 6 个协议绑定，风险较高。

#### 3.2.2 HTTP Pending Refs 仍为 O(n) 线性查找 (P2-16)

**现状**: `net_http_bind.cc:81` 使用 `std::find()` 在 `std::unordered_set<int>` 上查找:

```cpp
auto it = std::find(g_http_pending_refs.begin(), g_http_pending_refs.end(), ref);
```

`std::find` 是 O(n) 遍历，而 `unordered_set::find()` 是 O(1) 哈希查找。高并发 HTTP 下每个响应触发一次 O(n) 扫描，累积 O(n²) 开销。

**修复**: 一行改动: `auto it = g_http_pending_refs.find(ref);`

#### 3.2.3 class.lua isinstanceof 仍为 O(depth) (P3)

**现状**: `resources/script/runtime/common/class.lua:100` 的 `isinstanceof` 沿 `__index` 链逐级遍历:

```lua
function cls:isinstanceof(target)
    -- Walks the __index chain to find target among class ancestors.
```

**影响**: 深继承层级 + 高频调用（如每帧碰撞回调中检查实体类型）时累积开销不可忽视。优化方案：构建 ancestor set 缓存或使用直接标记。

#### 3.2.4 Config Reload 回调无订阅者 (P1-2 部分)

**现状**: `ConfigManager` 已实现 `RegisterReloadCallback` / `UnregisterReloadCallback` / `NotifyReloadCallbacks` 完整机制。但搜索全工程，**没有任何子系统调用 `RegisterReloadCallback`**。日志级别、定时器间隔、DB 连接池大小等配置实际不可运行时调整。

**影响**: 基础设施已建好但未使用——Reload 调用后只有 ConfigManager 自身数据更新，所有子系统继续使用旧配置。

#### 3.2.5 Lua 错误派发策略不统一 (P2-10)

**现状**: 4 种不同的错误处理模式共存:
- HTTP 绑定: `pcall` 安全回调
- TCP 绑定: `CallInstMethodStr` 包装
- KCP 绑定: 直接 `lua_pcall`
- Timer 绑定: `CallLuaFunction` 单日志

**影响**: 不同模块的错误行为不一致——有些静默吞错，有些写日志，有些崩栈。排查跨模块 Bug 时需要了解各模块的错误处理差异。

#### 3.2.6 全局变量追踪缺失 (P2-12)

**现状**: `ExportAll` 将数十个 C++ 函数注册到 Lua 全局表。`ScriptImporter::ClearCache()` 清空 `package.loaded` 但不清除全局变量。热更后旧模块的全局状态残留。

**影响**: 热重载模块后需要手动清理全局变量，否则旧状态与新加载的模块冲突。

#### 3.2.7 DoString 无脚本来源限制 (P2-23)

**现状**: `ScriptVM::DoString` 可从任意来源（网络、文件、数据库）执行 Lua 代码。无调用者身份追踪、无最大执行时间限制、无内存配额。

**影响**: 如果在运行时接收并执行远程脚本，攻击者可执行任意 Lua 代码。虽然沙箱限制了系统调用，但无限循环（`while true do end`）仍可阻塞整个服务器帧。

### 3.3 架构层面的缺失（README 目标对照）

#### 3.3.1 README 中的 "GameClient C API" 完整性待验证

README 描述 GameClient 为 "Pure C, ABI-safe surface" 支持 "TCP, UDP, KCP, HTTP, Timer, Log"。当前实现:
- TCP/UDP/KCP: ✓ 有实现文件
- HTTP: 未见 `client_http.cpp`
- 无客户端的 Lua 封装层 (server.lua/client.lua 仅用于服务端)

#### 3.3.2 服务端 HTTP Client

服务端缺少 HTTP 客户端的 Lua 绑定——当前 HTTP 绑定 (`net_http_bind.cc`) 仅实现 HTTP Server，无 HTTP Client 的 Lua API。

#### 3.3.3 缺少集成测试

22 个单元测试文件覆盖了各模块的独立功能，但缺少:
- Entity + TCP Server 联合测试（创建实体 → 客户端连接 → 消息收发）
- Physics + Entity 联合测试（物理碰撞 → 实体属性变更）
- DB + Entity 联合测试（ORM 加载实体 → 修改 → 持久化）
- 多 Space 压力测试

#### 3.3.4 UDP Server 缺少 Lua 封装

`resources/script/runtime/net/` 下仅有 `server.lua` (TCP) 和 `client.lua` (TCP) 封装。UDP/KCP Server/Client 在 Lua 侧无封装层，业务脚本需直接使用底层 C++ 绑定。

### 3.4 运行时健壮性不足

#### 3.4.1 物理 Recover 仍使用 100ms sleep

**现状**: `physics_thread.cc:153,166` 中，Recover 循环使用 `sleep_for(100ms)` 轮询，最长等待 5 秒。虽然有 event 通知机制，但 Recover 路径仍使用固定间隔轮询。

#### 3.4.2 MongoDB 响应队列满时丢弃最旧响应

**现状**: `db_thread.cc:228-233` 中，当响应队列满时，最旧的响应被静默丢弃（有 WARN 日志，但请求方收到的是超时，而非明确的"被丢弃"状态）。虽然有 `kDropped` 状态，但这是在请求入队时使用，响应丢弃路径不同。
