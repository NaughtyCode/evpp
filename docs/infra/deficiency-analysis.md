# CloudEngine Infrastructure Deficiency Analysis

## 概述

CloudEngine 的定位是"通用游戏服务器基础设施"——C++ 层实现基建（网络、定时器、数据库、物理），Lua 脚本层定义和执行业务逻辑。本文档从该定位出发，对工程现存的不足和缺陷进行系统性的深度分析。每一项分析包含**现状描述**、**风险/影响**和**改进方向**三个部分。

---

## 1. 架构层面的核心缺失

### 1.1 缺少 Actor / 实体模型

**现状**：引擎向下暴露的是原始的 TCP 连接回调（`on_connect`/`on_message`/`on_close`），没有 Actor、Entity 或 GameObject 的抽象层。`CustomPtrStore` 提供了 VM 级别的 `void*` 数组，但仅是裸指针存储，不提供任何实体生命周期管理。

**影响**：所有游戏服务器都需要管理成千上万的玩家、NPC、道具等实体——它们的创建/销毁、属性读写、定时行为、AOI（Area of Interest）同步。当前架构要求每个项目从零开始在 Lua 层构建这套体系，这不符合"基础设施"的定位。基础设施应当提供通用实体模型，业务层仅定义实体属性与行为。

**方向**：引入 Entity 基类（含 entity_id、属性表、定时器、所属场景/房间的绑定），由 C++ 管理生命周期和内存，Lua 侧通过继承定义业务逻辑。

---

### 1.2 缺少空间索引 / AOI 系统

**现状**：引擎没有任何空间划分、网格（grid）、四叉树（quadtree）或场景图（scene graph）的实现。物理子系统（Jolt Physics）虽然提供了碰撞检测的能力，但没有与"业务可见的视野管理"对接。

**影响**：AOI 是几乎所有多人在线游戏的基础需求——玩家只需要看到附近的实体，服务器只需要向附近的玩家广播状态变化。没有 AOI，每个项目都需要自行实现空间查找（"我周围 100 米有哪些玩家？"），且效率难以保证。

**方向**：提供基于网格或四叉树的标准 AOI 模块，支持实体进入/离开/移动时的回调，与网络广播层集成。

---

### 1.3 单 Lua VM 瓶颈

**现状**：`Engine` 持有唯一的 `ScriptVM`（即一个 `lua_State`），所有脚本执行——加载、每帧 Update、定时器回调、网络消息处理——都在这个单线程 VM 中完成。

**影响**：Lua 的单线程执行是游戏服务器的核心性能瓶颈。无论配置了多少 CPU 核，所有业务逻辑都被串行化。对于需要支持数千并发玩家的服务器来说，单 VM 架构不可扩展。

**方向**：
- 多 VM 池方案：每个场景/房间一个独立 VM，不同 VM 可以并行运行在不同线程上
- 或 Actor-per-VM 方案：每个 VM 管理一组实体的逻辑
- 跨 VM 消息传递机制（VM 间 RPC）

---

### 1.4 缺少服务间 RPC 框架

**现状**：evpp 提供了 TCP/UDP/HTTP/KCP 四种网络传输，但全部是原始字节流/消息回调模式。没有序列化协议层（protobuf/flatbuffers/msgpack 集成），没有 IDL（接口定义语言），没有 RPC 桩代码生成。

**影响**：生产环境的游戏服务器几乎从不以单进程方式运行。典型集群包含：网关服务器（Gateway）、游戏逻辑服务器（Game）、聊天服务器（Chat）、匹配服务器（Matchmaking）、数据库代理（DB Proxy）等。服务间通信需要一个高效的 RPC 框架。当前架构下，每个项目都需要自行设计协议格式和消息路由。

**方向**：提供基于 msgpack 或 flatbuffers 的内置 RPC 层，支持 request/response、push、broadcast 三种语义，支持服务发现和负载均衡。

---

### 1.5 缺少完整的序列化/反序列化框架

**现状**：msgpack 模块以 Lua 绑定的形式存在，允许在 Lua 中 `pack`/`unpack`，但没有将其连接到网络层、持久化层或实体同步层。

**影响**：游戏中需要序列化的场景非常多——网络消息打包、玩家存档保存/加载、配置下发、状态同步。每处都需要开发者手动处理 pack/unpack 及版本兼容问题。

**方向**：提供声明式的实体属性标记（如 `@sync`/`@persist`），基础设施自动管理同步和持久化的序列化流程。

---

### 1.6 缺少热更新系统

**现状**：`ScriptImporter` 提供了模块搜索和缓存机制，可以 `ClearCache(L)` 清除 require 缓存。`class.lua` 中有一个基于弱引用的注册表，支持类被重新定义时复用旧表。但这些只是零散的零件，没有形成完整的热更新流程。

**影响**：在线运营的游戏服务器需要在不中断服务的前提下更新业务逻辑（修 bug、调整数值、上新活动）。没有热更新机制意味着每次更新都需要停服，这是不可接受的。

**方向**：提供标准的热更新流程——文件监控检测变更 → 重新加载模块 → 更新已有实例的方法表 → 迁移数据（如有必要）→ 验证 → 提交或回滚。

---

### 1.7 缺少服务发现 / 集群管理

**现状**：没有服务注册、服务发现、健康检查、主节点选举、配置中心等集群基础设施。

**影响**：多服务集群需要知道"有哪些服务在线、地址是多少、是否健康、哪个是主节点"。没有这些能力，运维需要手动管理服务拓扑。

---

### 1.8 生命周期模型过于简化

**现状**：引擎的生命周期是线性的：`Init → Start → Run → Shutdown`，对应 Lua 的 `InitScript → (每帧 UpdateScript) → DestroyScript`。没有场景切换、加载过渡、分阶段初始化、优雅降级等概念。

**影响**：实际游戏服务器通常有复杂的生命周期——"加载配置 → 连接数据库 → 预加载场景 → 开放登录 → 关闭登录 → 踢出玩家 → 保存数据 → 停止"。当前模型无法表达这些阶段。

**方向**：引入状态机和生命周期阶段（Phase），允许业务层定义每个阶段的进入/退出回调，支持阶段间的过渡动画（如 loading screen）。

---

## 2. 网络层的缺失

### 2.1 缺少消息分帧/分隔协议

**现状**：TCP 的 `on_message` 回调收到的是原始字节（`Buffer*`），没有内置的粘包/拆包处理。UDP/KCP 的回调也是原始数据报。

**影响**：TCP 是流协议，需要应用层定义消息边界。几乎所有游戏协议的第一个需求就是消息分帧（长度前缀或分隔符）。当前架构让每个用户在 Lua 层自行处理粘包——而 Lua 的字符串处理效率远低于 C++。

**方向**：在网络层提供内置的 `LengthPrefixedCodec` / `DelimiterCodec`，自动拆包后再分发完整消息给 Lua。

---

### 2.2 缺少连接级会话管理

**现状**：`TCPServer` 用 `std::map<uint64_t, TCPConnPtr>` 追踪连接，但没有为每个连接附加业务数据（如 player_id、认证状态、最后活跃时间）的标准方式。Lua 绑定层通过 `ConnCtx` 关联了一个 Lua 实例引用，但这是绑定层的实现细节而非公开 API。

**影响**：游戏服务器需要在连接上附加大量上下文——玩家 ID、认证令牌、角色对象指针、心跳计时器。当前需用户在 Lua 侧自行维护映射表。

**方向**：为连接提供 `userdata` / `context` 字段，支持在 C++ 和 Lua 侧双向读写。

---

### 2.3 缺少内置加密

**现状**：evpp 有 HTTP SSL 支持（`httpc/ssl.h`），但 TCP/UDP/KCP 连接没有内置加密机制。

**影响**：任何面向公网的服务器都需要连接加密（防止中间人攻击、保护用户数据）。在每个项目 Lua 层实现加密非常不现实。

---

### 2.4 缺少消息优先级队列

**现状**：所有发送的消息以 FIFO 顺序进入发送缓冲区。

**影响**：游戏中不同类型消息的优先级不同——位置同步 > 技能释放 > 聊天消息 > 系统通知。在网络拥塞时，低优先级消息应在高优先级消息之前被丢弃。

---

### 2.5 缺少带宽管理和限流

**现状**：没有每连接发送速率限制、没有全局带宽上限、没有消息合并（batching）机制。

**影响**：单个异常客户端（或恶意客户端）可能耗尽服务器带宽，影响其他正常玩家。无消息合并则导致大量小包发送，降低网络效率。

---

### 2.6 缺少断线重连机制

**现状**：`TcpClient` 有基本的 reconnect 测试，但连接断开后需要用户完全重建连接和状态。没有 session token 重连、没有消息重放、没有状态恢复。

**影响**：移动网络环境下断线是常态。良好的重连体验是游戏服务器的基础能力。

---

## 3. 脚本系统的风险与不足

### 3.1 缺少沙箱安全机制

**现状**：`ScriptVM` 构造函数中调用 `luaL_openlibs(L_)`，加载了全部 Lua 标准库，包括 `os`（可执行系统命令）、`io`（可读写文件）、`debug`（可操纵 VM 内部状态）。

**风险**：业务脚本中的任何漏洞（如通过用户输入注入的 `os.execute("rm -rf /")`）都可能造成灾难性后果。对于"通用基础设施"来说，应当默认安全，由用户选择开放危险能力。

**方向**：默认关闭 `os.execute`/`os.remove`/`io.open` 等危险函数，通过白名单机制由用户显式开放。

---

### 3.2 缺少协程集成

**现状**：Lua 5.5 内置了协程（coroutine）支持，但引擎没有提供任何协程调度器。异步操作（如数据库查询、RPC 调用）无法以 `await` 风格编写 Lua 代码，只能用回调地狱。

**影响**：看看 `test_net_client_server.lua` 的测试代码——异步测试需要通过层层回调嵌套，创建 timer 来轮询完成条件。这在业务代码中会迅速变得不可维护。

**方向**：提供 `async_call` / `await` 原语，引擎负责在异步操作完成时 resume 协程。

---

### 3.3 缺少 Lua 错误恢复机制

**现状**：`ScriptVM::CallGlobalFunction` 中 `UpdateScript` 如果出错只记录日志（带 5 秒限流），`InitScript` 和 `DestroyScript` 出错记录 Error 级别日志。VM 在出错后可能处于栈不一致状态（`lua_pop` 只弹 1 个），缺乏系统性的错误恢复流程。

**影响**：单次业务脚本错误可能导致 VM 栈状态损坏，后续所有脚本执行都可能异常。生产环境中，一个活动脚本的 bug 可能导致整个服务器不可用。

---

### 3.4 全局函数钩子脆弱

**现状**：生命周期依赖全局函数 `InitScript`/`UpdateScript`/`DestroyScript`。如果任何被 `import` 的共享模块中意外定义了同名全局函数，会覆盖期望的业务逻辑。

**影响**：在多人协作的项目中，命名冲突几乎是必然的。且引擎无法区分"有意定义"还是"意外覆盖"。

**方向**：使用基于注册的模式——入口脚本 `register_lifecycle_handler()` 显式注册，而非搜索全局函数。

---

### 3.5 缺少 Lua 侧的内存和性能分析

**现状**：`ProfilerManager` 基于 Perfetto，可以在 C++ 层追踪帧时间（`ENGINE_PROFILE_SCOPE`），但没有 Lua 级别的函数耗时统计、GC 追踪、内存分配追踪。

**影响**：业务逻辑在 Lua 中运行，当出现性能问题时，开发者无法定位是哪个 Lua 函数、哪个脚本模块导致的慢帧或内存泄漏。

---

### 3.6 import 系统缺少依赖图与循环检测

**现状**：`ScriptImporter` 是路径搜索 + `package.loaded` 缓存模式。没有构建模块依赖图，没有检测循环依赖（Lua 自身的 require 会导致栈溢出或返回不完整的模块）。

**影响**：随着业务模块增多，依赖关系变得复杂，循环依赖可能悄悄引入并导致难以排查的运行时问题。

---

## 4. 数据库层的局限

### 4.1 仅支持 MongoDB

**现状**：数据库层（`database/mongo/`、`database/mongo_bind/`、`database/data_service/`）完全绑定 MongoDB。没有抽象接口可以切换到 MySQL、PostgreSQL、Redis 等其他存储。

**影响**：不同游戏对数据库的需求差异很大——有些需要关系型 DB（账号系统），有些需要 Redis（排行榜），有些项目因为合规要求不能使用 MongoDB。"通用基础设施"应该支持多后端。

**方向**：定义抽象的 `IDataStore` 接口（CRUD + Query），MongoDB 作为第一个实现，后续可添加 MySQL/Redis 后端。

---

### 4.2 缺少 ORM / 对象-文档映射

**现状**：数据库操作需要手动构造 BSON/JSON 文档（`bson_data` / `bson_data2` 字符串字段），手动解析返回结果（`result_data` JSON 字符串）。

**影响**：当实体有几十个字段时，手动序列化/反序列化是大量重复劳动且容易出错。缺少 ORM 意味着没有字段类型校验、没有迁移工具、没有索引自动管理。

---

### 4.3 缺少缓存层

**现状**：`DatabaseService` 每次请求都直接走 SPSC 队列 → DBThread → MongoDB 网络 IO。没有进程内缓存（如 LRU Cache），也没有 Redis 集成。

**影响**：玩家数据（尤其是热数据——在线玩家的档案）在每个操作中都重新从数据库读取是不可接受的性能开销。

**方向**：提供实体级缓存（自动加载/写回/淘汰），支持 write-through / write-behind 策略。

---

### 4.4 DatabaseService 操作集封闭

**现状**：`DbOperation` 是一个固定的枚举（13 种操作），不支持用户从 Lua 侧注册自定义操作。

**影响**：如果业务需要特殊的数据库操作（如聚合管道、事务、GridFS 文件操作），要么走 `kExecuteScript`（性能差），要么修改 C++ 代码。

---

## 5. 配置系统的不足

### 5.1 缺少运行时热更新通知

**现状**：`ConfigManager::Reload()` 重新从磁盘加载 JSON 文件，但没有任何回调或监听机制通知运行中的子系统（如网络服务器、物理系统）"配置已变更"。

**影响**：运行时修改了配置（如调整帧率、切换数据库地址），变更不会生效，因为各子系统持有的是旧配置的副本。这使 Reload 功能形同虚设。

---

### 5.2 缺少 Schema 校验

**现状**：glaze 做 JSON 反序列化时，如果缺少字段就使用默认值，如果字段类型不匹配可能导致反序列化失败（返回 false）。但没有字段范围校验、没有枚举值校验、没有必填字段标记。

**影响**：一个拼写错误的配置（如 `"target_fps": 0`）不会被检测到，直到运行时出现除零或其他未定义行为。

---

### 5.3 配置分离不灵活

**现状**：配置类型被硬编码为 `RuntimeConfig` / `ClientConfig` / `ServerConfig` 三个结构体，分别从三个固定路径加载。用户无法在不修改 C++ 的情况下增加新的配置域。

**方向**：提供通用 key-value 配置注册机制，允许 Lua 侧声明和读取自定义配置段。

---

## 6. 定时器系统的问题

### 6.1 定时器层级过度设计

**现状**：`TimerManager` 同时支持高精度定时器（ns 级）、时间轮（ms 级）、闹钟定时器三种类型，每种有独立的创建/启动/取消 API，外加多种时钟源（TAI/boottime/monotonic/coarse）。

**影响**：对于游戏服务器，绝大多数定时需求是毫秒级的超时和间隔。三种定时器类型增加了 API 表面积和使用者的认知负担，且不同定时器类型在 Lua 绑定中被平铺为全局函数，混淆使用者。

**方向**：服务器侧简化为一套统一 API，由引擎内部选择最优实现。

---

### 6.2 缺少 Lua 定时器自动生命周期管理

**现状**：Lua 定时器绑定（`timer_bind.cc`）创建定时器后会返回 timer_id，用户需手动取消。如果用户忘记取消，或绑定的对象已被销毁，定时器仍会触发并可能访问已释放的数据。

**方向**：将定时器与 Entity/VM 生命周期绑定——对象销毁时自动取消其关联的定时器。

---

## 7. 物理子系统的耦合问题

### 7.1 物理结果未接入游戏对象和网络同步

**现状**：`Engine::FrameLoop()` 中调用 `PhysicsEngineBridge::FetchResult()`，但其返回的 transforms 和 diff_packets 处理代码是注释掉的（"would go here"）。

**影响**：物理系统虽然初始化并运行了，但从游戏服务器角度看并未产生实际效果——物理模拟的结果没有更新到游戏实体，也没有通过网络同步给客户端。

---

### 7.2 物理配置路径硬编码

**现状**：`Engine::Init()` 中物理配置路径是通过字符串拼接构造的：
```cpp
auto phys_cfg = runtime_cfg.resource_dir + "/physics/configs";
auto phys_data = runtime_cfg.resource_dir + "/physics/data/scene.json";
```
场景数据路径 `scene.json` 是写死的单文件，不支持多场景。

---

## 8. 测试覆盖严重不足

### 8.1 现状

| 测试类型 | 覆盖范围 | 缺失 |
|----------|---------|------|
| 单元测试 | evpp 网络层（buffer/tcp/http/udp/event_loop） | 所有 engine 层级 |
| 冒烟测试 | 仅 physics_smoke | 引擎启动、脚本加载、完整链路 |
| 稳定性测试 | stability.cc（单文件） | 长时间运行、内存泄漏检测 |
| 集成测试 | 无 | 端到端 |
| 性能测试 | io/throughput 微基准 | 帧循环、脚本执行、数据库操作 |
| Lua 测试 | test_net_client_server.lua | log/timer/msgpack/mongo/physics |

### 8.2 具体缺失

- **Engine 生命周期**：没有测试 Init/Start/Run/Shutdown 的完整流程
- **配置加载**：没有测试各种配置组合、错误配置的容错
- **脚本 VM**：没有测试 DoString/DoFile/DoDirectory 在各种输入下的行为
- **定时器**：没有测试 TimerManager 的三种定时器类型的正确性
- **数据库服务**：没有测试 SPSC 队列的并发正确性、背压行为
- **Lua 绑定**：log/timer/net/msgpack/mongo 的绑定函数没有自动化测试
- **并发安全**：没有压力测试验证多线程场景下的数据竞争

**影响**：无测试覆盖意味着每次修改 C++ 基建层都无法自信地验证回归。对于"通用基础设施"来说，可靠性是核心价值主张。

---

## 9. 构建和工程化问题

### 9.1 第三方依赖管理混乱

**现状**：所有第三方库以源码或预编译包形式放入 `src/thirdparty/`（lua、libevent、quill、glaze、kcp、JoltPhysics、concurrentqueue、gflags、gtest、rapidjson、perfetto、mongo-c-driver、libhashkit、memcached、mysql、win32code 等 16+ 个依赖）。没有包管理器（vcpkg/Conan/CMake FetchContent），没有依赖版本锁定文件。

**影响**：新成员搭建开发环境困难，依赖升级需要手动替换文件夹，不同开发者可能使用不同版本的依赖导致构建不一致。

---

### 9.2 缺少 CI/CD

**现状**：没有 `.github/workflows/` 或任何 CI 配置文件。

**影响**：没有自动化构建、测试、静态分析、格式检查。代码质量完全依赖人工。

---

### 9.3 缺少代码规范工具

**现状**：`src/thirdparty/` 中有 astyle，但没有 `.clang-format` 配置文件，没有 `.clang-tidy`，没有集成到构建流程。

**影响**：多人协作时代码风格不统一，容易产生无意义的格式 diff。

---

### 9.4 copy_resources 总是全量复制

**现状**：`CMakeLists.txt` 中 `copy_resources` 自定义目标使用 `copy_directory`，每次构建都完整复制整个 `resources/` 目录到输出路径，没有增量复制机制。

---

### 9.5 Windows 偏向

**现状**：`engine_api.h` 有大量 Windows 条件编译、`event_loop.h` 依赖 `winsock2.h`、`server.cc` 有 WSAStartup/WSACleanup 封装。虽然有 Linux 分支但明显以 Windows 为主要开发平台。

**影响**：游戏服务器的主流部署平台是 Linux。如果 Linux 是二等公民，生产环境的兼容性和性能需要额外验证。

---

## 10. 可观测性缺失

### 10.1 缺少生产级监控指标

**现状**：`ProfilerManager` 基于 Perfetto，是开发期的离线 trace 工具，不适合生产环境持续监控。没有内置的 metrics 采集——连接数、消息速率、帧时间分布、内存使用、延迟百分位、错误计数等。

**影响**：生产运维时无法快速定位性能瓶颈或异常状态。

---

### 10.2 缺少管理/运维 HTTP 接口

**现状**：没有 built-in HTTP admin endpoint（如 `/health`、`/stats`、`/config`、`/gc`）。

**影响**：无法通过 API 查询服务状态、触发 GC、临时调整日志级别，运维操作需要登录服务器或修改配置文件重启。

---

### 10.3 调试 fprint 散落生产代码

**现状**：`engine.cc` 和 `server.cc` 中有大量 `std::fprintf(stderr, ...)` 调用，混合在 Quill 结构化日志与 stderr 调试输出之间。

**影响**：stderr 输出无时间戳、无日志级别、无法被日志收集系统抓取。这些调试输出不应出现在生产路径中。

---

## 11. 代码设计质量

### 11.1 单例滥用

**现状**：以下类全部是单例：`Engine`、`ConfigManager`、`TimerManager`、`PhysicsEngineBridge`、`DatabaseService`、`ProfilerManager`。

**影响**：
- 无法在一个进程中运行多个隔离的引擎实例（如同时运行游戏服务器和内部管理服务器）
- 单例的隐式依赖使单元测试极其困难——无法 mock、无法隔离
- 单例的生命周期管理依赖隐式的构造/析构顺序，容易导致 use-after-free

**方向**：将核心类改为可实例化的常规对象，通过依赖注入传递依赖。单例仅保留为可选的便捷访问器（如当前 `TimerManager::instance()` 的用法）。

---

### 11.2 错误处理不一致

**现状**：
- `ScriptVM::DoFile()` 返回 `bool` + 可选 `error_out` 参数
- `Engine::Init()` 的 physics 初始化失败只打 WARN，不影响后续流程
- `GetScriptVM()` 在 VM 未初始化时调用 `abort()`
- 网络绑定中部分函数返回错误码，部分通过 `luaL_error` 抛 Lua 异常

**影响**：调用方无法形成统一的错误处理模式，需要查阅每个具体函数的文档才能确定如何处理失败。

---

### 11.3 头文件包含过多实现细节

**现状**：`engine.h` 直接 include `runtime/evpp/invoke_timer.h`、`runtime/config/config.h`、`runtime/core/engine_api.h`。修改对 `InvokeTimer` 的任何依赖会导致间接重编译所有包含 `engine.h` 的文件。

**方向**：使用前置声明 + Pimpl（pointer-to-implementation）模式减少头文件依赖。

---

### 11.4 大文件的职责混杂

**现状**：`net_server_bind.cc`（~22KB）同时包含：
- Server 创建/销毁/启停
- Connection 的 send/close/remote_addr
- Callback 分发（on_connect, on_message, on_close, on_error）
- 全局 server 注册表（`g_server_ctxs`）用于 shutdown 清理
- ConnCtx / ServerCtx 内部数据结构

**方向**：拆分为 server lifecycle、connection operations、callback dispatch 三个文件。

---

### 11.5 缺少编译防火墙

**现状**：头文件中大量使用模板和 inline 函数（如 `timer_manager.h` 包含全部实现，`custom_ptr_store.h` 中所有方法都有完整实现），导致修改实现即触发大规模重编译。

---

## 12. 总结：功能完整性评分

基于"通用游戏服务器基础设施"的定位，以下是对各子系统的完备性评估：

| 子系统 | 当前状态 | 完备度 | 说明 |
|--------|---------|--------|------|
| 事件循环 / 网络 IO | 可用 | ★★★★☆ | evpp 有多协议支持，但缺消息分帧和安全层 |
| 定时器 | 可用 | ★★★★☆ | 功能丰富但层级过重，缺乏 Lua 侧生命周期绑定 |
| 日志 | 可用 | ★★★★☆ | Quill 异步日志，功能完备 |
| 脚本 VM | 基础可用 | ★★★☆☆ | 有 import 系统和 bindings，但缺沙箱、协程、热更 |
| 脚本绑定 | 基础可用 | ★★★☆☆ | 覆盖了核心能力（net/timer/log/msgpack/db），但缺乏高层抽象 |
| 配置管理 | 基本可用 | ★★★☆☆ | JSON 加载可用，但缺校验、热通知、扩展性 |
| 数据库 | 基础可用 | ★★★☆☆ | MongoDB 绑定完整，但缺 ORM、缓存、多后端 |
| 物理 | 部分可用 | ★★☆☆☆ | 引擎已集成但结果未接入游戏对象和同步 |
| 测试 | 严重不足 | ★☆☆☆☆ | 仅 evpp 层有单测，大部分核心模块无覆盖 |
| **实体模型** | **缺失** | ★☆☆☆☆ | 无 Actor/Entity/GameObject 框架 |
| **AOI** | **缺失** | ☆☆☆☆☆ | 无空间索引、无视野管理 |
| **RPC** | **缺失** | ☆☆☆☆☆ | 无服务间通信框架 |
| **序列化框架** | **缺失** | ★☆☆☆☆ | 有 msgpack 绑定但不集成到实体和网络 |
| **集群管理** | **缺失** | ☆☆☆☆☆ | 无服务发现、无注册中心 |
| **热更新** | **缺失** | ★☆☆☆☆ | 有零件（类注册表、缓存清除）但无完整流程 |
| **对象池/内存** | **缺失** | ☆☆☆☆☆ | 无内置对象池或内存管理策略 |
| **认证/安全** | **缺失** | ☆☆☆☆☆ | 无内置认证框架、脚本无沙箱 |
| **监控运维** | **缺失** | ★☆☆☆☆ | 仅开发期 trace，无生产监控指标 |

## 13. 优先级建议

基于"基础设施先行，业务后行"的原则，建议按以下优先级弥补关键缺失：

**P0（阻塞业务开发的基础设施）**：
1. 实体模型（Entity/Actor 抽象）
2. 消息分帧协议（从原始字节到结构化消息）
3. 多 VM 架构（去掉单线程瓶颈）
4. 测试基础设施（确保基建可靠性）

**P1（大幅提升开发效率）**：
5. 服务间 RPC 框架
6. 热更新系统
7. 脚本协程集成（告别回调地狱）
8. 配置热通知

**P2（生产就绪）**：
9. AOI 系统
10. 序列化/ORM 框架
11. 监控和运维接口
12. 沙箱加固

**P3（完善优化）**：
13. 缓存层
14. 多数据库后端
15. CI/CD
16. 消息优先级/限流
