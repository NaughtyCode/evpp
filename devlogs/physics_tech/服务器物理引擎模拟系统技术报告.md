# 服务器物理引擎模拟系统技术报告

## 1. 概述

本报告定义了一套运行于服务器端的物理引擎异步模拟系统架构。系统将物理模拟完全隔离在独立线程中，通过**命令驱动**与**结果回传**机制与主逻辑线程交互，支持从资产文件加载完整物理场景，并原生支持对变化数据的**增量序列化**，以满足高性能、低带宽的服务端需求。

### 核心目标

| 目标 | 说明 |
|---|---|
| **独立物理线程** | 物理模拟在独立线程中运行，避免阻塞主逻辑 |
| **数据驱动** | 物理场景及物体完全由资产文件定义 |
| **增量同步** | 物体状态序列化时仅输出发生变化的数据，减少网络开销 |
| **并行处理** | 主线程每帧触发模拟，在恰当时机获取结果，实现并行 |

---

## 2. 系统架构

系统采用 **命令队列 + 结果队列** 的异步通信模型，物理线程与主线程间仅通过线程安全的无锁队列交换数据，无共享内存依赖。

```
┌──────────────────┐    命令队列 (SPSC)    ┌──────────────────┐
│     主线程       │ ── Spawn / Tick ──► │    物理线程      │
│  · 游戏逻辑      │                      │  · 场景管理       │
│  · 网络同步      │ ◄─ FrameResult ──── │  · 物理步进       │
│  · 序列化        │    结果队列 (SPSC)    │  · 变化提取       │
└──────────────────┘                      └──────────────────┘
```

- **主线程** 将玩家输入、系统事件等封装为命令，写入命令队列
- **物理线程** 从命令队列中读取并执行，完成物理步进后，将变换快照、碰撞事件及变化数据打包为结果，写入结果队列
- **主线程** 在完成非依赖任务后，等待本帧结果就绪，再更新游戏状态并下发网络数据

---

## 3. 物理线程设计

物理线程运行独立事件循环，以帧号同步为主要时序保证。

### 3.1 初始化

线程启动时加载指定的物理资产文件（如 `scene.physics`），构建完整物理世界，包括：

- 静态碰撞体及其形状、材质
- 动态物体原型（质量、惯性、形状、摩擦/弹性等）
- 全局参数（重力、求解器迭代次数、固定子步长等）

加载完毕后进入主循环等待命令。

### 3.2 命令处理

物理线程持续执行以下循环：

1. 从命令队列出队一个命令（可设置超时以支持优雅退出）
2. 根据命令类型执行：

| 命令 | 说明 |
|---|---|
| `Spawn(protoId, transform)` | 基于原型动态生成刚体并加入世界 |
| `Destroy(objectId)` | 移除并销毁指定刚体 |
| `ApplyForce` / `SetVelocity` | 即时物理操作 |
| `Tick(frameId, deltaTime)` | 进入物理模拟流程（见 3.3） |

非 `Tick` 命令立即处理，`Tick` 命令为每帧模拟的触发器。

### 3.3 物理步进与结果生成

收到 `Tick` 命令后执行：

```
PhysicsWorld.Step(deltaTime);
```

模拟过程中使用**固定子步长**（如 1/120 秒）以保证确定性。步进完成后：

1. **提取变换快照** — 遍历所有活跃动态刚体，记录当前 Transform（位置 + 旋转）
2. **提取碰撞事件** — 收集本帧内新产生、持续或结束的碰撞对
3. **生成变化差异（Diff）** — 对每个被标记为"已变化"的物体（由物理引擎内部在属性写时标记），生成相对于上一物理帧的变化包 `DiffPacket`，包含物体ID、变化掩码及变化的字段值；生成后清除变化标记
4. 将上述所有数据连同 `frameId` 封装为 `PhysicsFrameResult`，推入结果队列

## 4. 资产文件设计

物理场景资产采用结构化文本或二进制格式，与渲染逻辑完全解耦。

示例结构：

```json
{
  "gravity": [0, -9.81, 0],
  "solverIterations": 10,
  "subStepCount": 3,
  "staticBodies": [
    {
      "id": "ground",
      "shape": { "type": "box", "halfExtents": [100, 0.5, 100] },
      "material": { "friction": 0.8, "restitution": 0.1 }
    }
  ],
  "dynamicPrototypes": [
    {
      "protoId": "player_default",
      "shape": { "type": "capsule", "radius": 0.5, "height": 1.8 },
      "mass": 80,
      "material": { "friction": 0.3, "restitution": 0.0 }
    }
  ]
}
```

- **`staticBodies`** — 在物理线程加载时直接构建不可移动的碰撞体
- **`dynamicPrototypes`** — 供主线程通过 `Spawn` 命令引用，物理线程根据原型克隆创建实例
- 资产可包含自定义物理材质、约束模板等，完全覆盖物理世界构建需求

## 5. 增量序列化（只序列化变化数据）

系统将增量序列化拆分为两个阶段：**物理线程生成原始变化包（Diff）**，**主线程结合客户端状态生成最终网络增量**。

### 5.1 物理线程生成 DiffPacket

每个需要同步的物体在物理线程中维护一个"上一帧物理状态"的副本，用于帧间比较：

```
DiffPacket {
    uint32 objectId;
    uint16 changeMask;   // bit0: position, bit1: rotation, bit2: linearVel, ...
    float  values[];     // 按掩码顺序排列的变化值（可选定点压缩）
}
```

比较基于**阈值判断**（如位置变化 < 1mm、旋转角度 < 0.01° 则视为不变），仅当有字段变化超过阈值时才生成 `DiffPacket`。物理线程产出的即为最原始的、仅包含变化的物理数据，不涉及任何客户端确认状态。

### 5.2 主线程生成网络增量

主线程维护每个客户端-物体的**复制状态跟踪器**，记录该客户端上次确认的物体状态（位置、旋转等）。收到 `PhysicsFrameResult` 后：

1. 对每个物体，使用物理 Diff 更新自己维护的"权威状态"
2. 结合该客户端上次确认状态与权威状态，计算需要下发的增量变化
3. 将增量序列化后发送，并更新客户端的"已确认状态"

> 此设计使得网络同步策略（全量/增量、可靠性等）完全由主线程控制，物理线程不感知网络细节，满足"只序列化变化数据"的要求。

---

## 6. 主线程帧循环与结果获取时机

主线程每帧执行严格的时序流程，最大化利用物理线程的并行计算能力：

```
主帧循环：

1. 生成新帧号 frameId，处理网络输入，生成物理命令并写入命令队列
2. 写入 Tick(frameId, fixedDeltaTime) 命令，触发物理线程开始模拟
3. 执行非物理依赖任务（AI 决策、定时器、聊天处理等）
4. 调用 FetchResult(frameId, timeout) 等待本帧物理结果
   （一般此时物理线程早已完成，等待时间极短）
5. 使用结果中的变换快照更新游戏对象状态
6. 处理碰撞事件，触发伤害、拾取等游戏逻辑
7. 基于结果中的 Diff 数据，为各客户端构建增量同步包并发送
8. 进入下一帧循环
```

### 获取结果时机的合理性

- 步骤 2 触发模拟后，物理线程立即开始计算，主线程不空闲等待，转而处理步骤 3 中的并行任务
- 当主线程必须依赖物理结果继续（步骤 5-7）时，物理模拟基本已经完成，实现**几乎零等待**的高效并行

### 超时与容错

`FetchResult` 使用带超时的等待，若物理线程崩溃或严重延迟，主线程可安全进入异常处理流程（如重启物理线程、断开客户端等），避免整个服务瘫痪。

---

## 7. 线程安全与通信机制

| 机制 | 说明 |
|---|---|
| **命令队列** | 单生产者单消费者（SPSC）无锁队列（如 `moodycamel::ReaderWriterQueue`），物理线程为消费者，主线程为生产者 |
| **结果队列** | 同样采用无锁 SPSC 队列，物理线程将结果 `PhysicsFrameResult` 整体移动入队；结果数据使用 `std::vector` 存储以减少动态分配 |
| **帧号同步** | `PhysicsFrameResult` 严格绑定帧号，主线程仅接受期望帧号的结果，防止因队列堆积导致错帧 |
| **内存管理** | 结果结构体使用移动语义，可采用对象池复用底层内存，进一步降低分配频率 |

---

## 8. 容错与健壮性

- **物理线程异常退出** — 命令队列支持关闭信号，主线程检测到结果超时后标记线程需重启，并在安全点重新初始化物理世界
- **资产加载失败** — 物理线程启动时将错误汇报给主线程，阻止服务进入可服务状态
- **固定时间步长** — 服务器采用固定帧间隔调用 `Tick`，避免浮点累积误差，保证跨平台确定性（若物理引擎支持）
- **变化阈值** — Diff 生成使用的 epsilon 值可配置，以平衡精度与网络带宽

---

## 9. 总结

本设计通过**独立物理线程、资产驱动场景、帧号同步与增量序列化分离**，构建了一个高性能、可扩展的服务端物理模拟系统。

### 关键优化点

| 优化点 | 说明 |
|---|---|
| **完全并行** | 主线程在物理模拟期间执行无依赖任务，有效隐藏延迟 |
| **低带宽序列化** | 变化数据由物理线程直接提取，主线程按客户端状态二次增量，大幅减少同步数据量 |
| **高可靠性** | 帧号强匹配、超时保护与无锁通信，确保系统在异常情况下仍可控制 |

该架构可直接应用于需要**服务端权威物理**的多人游戏、物理模拟服务等场景。
